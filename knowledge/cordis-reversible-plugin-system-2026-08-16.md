## 引言：一个让你抓狂的日常场景

想象你写了一个聊天机器人，它有一个"每日新闻推送"插件，每天早上 8 点定时发消息。运行三个月后，你想把这个功能撤掉——产品改版了。

你打开代码，把注册这个插件的两行删掉。然后你发现，**服务必须重启**才能生效。而重启意味着：

- 内存里积累的缓存全部丢失
- 正在进行的 300 个对话会话全部中断
- 连接着的数据库连接池要重新建立
- 可能还要等几分钟才能恢复服务

"为什么我删一个功能，必须让整个服务死一次？"

这个问题不是聊天机器人的专利。**Koa 注册了中间件就没有 API 能撤销；Vue 注册了组件就没有 API 能卸载；Node.js 加载了 `.node` 原生模块就永久占用**。现代软件框架在"组装"这件事上很擅长，在"拆卸"这件事上却集体失语。

VSCode 是规模最大的受害者：它的 Top 100 扩展里，**87 个含可执行代码的扩展，卸载时都必须重启整个编辑器**（2026 年 6 月 Marketplace 数据）。

本文要讲的 Cordis——一个只有 2000 行左右核心代码的插件框架——就是为解决这个问题而生的一套完整方案。它后来被 DeepSeek 采用，成为了 DeepSeek Harness（dsh）智能体框架的内核。理解它，你就理解了"可热插拔软件"的全部原理。

## 第一部分：问题是什么——三个维度的"不可逆病"

先给这个问题起个正式名字：**动态组合（Dynamic Composition）**——在软件运行时添加、移除、替换组件的能力。它的反面是静态组合：函数调用、import、继承，编译期就定死了，运行后一成不变。

动态组合的病，可以精确地拆成**三个维度**：

### 问题 1（时间维度）：卸载了，但痕迹还在

```js
// 你注册了一个中间件
app.use(checkLogin)

// 现在想撤掉它——Koa 说：对不起，没有这个 API
```

一个组件运行时做了一堆事：注册了事件监听器、打开了文件、占用了端口、写了全局配置。**卸载时，这些"事"没有人收拾**。用专业的话说：组件对环境产生了**副作用（Side Effect）**，却没有配套的**撤销手段**。

更糟的是，这个病会**传染**。B 插件依赖 A 插件注册的一个事件；你卸载 A 时 B 还在监听——之后 B 的行为就变得不可预测。这种"卸载残留"是生产环境里最难查的一类 bug。

### 问题 2（空间维度）：依赖关系没人管

组件的另一面是依赖：B 插件要用 A 插件提供的数据库服务。现实中：

- A 还没加载好，B 就启动了 → B 读到空引用，崩溃
- A 被卸载了，B 不知道 → B 下次调用直接报错
- A 被替换成 A'（换了个数据库），B 还握着 A 的旧引用

传统的解法是**加载顺序**："先加载 A 再加载 B"——把空间问题硬编码进时间顺序。一旦组件多了（Koishi 生态有 4000+ 插件），手排顺序就崩溃了。

### 问题 3（组合维度）：路径依赖

最隐蔽的一个问题：同一个系统，**插件的加载顺序不同，最终行为就不同**。你部署了 A、B、C 三个插件，用户报告 bug 你复现不了——因为你的本地加载顺序和生产不一样。

理想的状态是**路径无关（Path Independence）**：不管中间怎么折腾（装了又卸、卸了又装、换了顺序装），最终行为只取决于**最终启用了哪些插件**。中间的过程不留任何痕迹。

## 第二部分：逐个击破——从直觉到代码

### 解法 1：给每个副作用配一个"撤销按钮"

第一个洞见来自最朴素的编程习惯——**函数返回值**：

```ts
// 传统写法：serve 函数开了端口，但谁也不知道怎么关
function serve(port: number) {
  const server = createServer().listen(port)
}

// 可逆写法：把"怎么关"作为返回值，跟着"怎么开"走
function serve(port: number) {
  const server = createServer().listen(port)
  return () => server.close()   // ← 撤销按钮
}

const dispose = serve(80)   // 启动服务，顺手拿到撤销按钮
dispose()                   // 按下按钮，端口释放，一切还原
```

规则只有一条：**每个原子操作，正向做一步，反向退一步，反向动作必须和正向动作写在一起**。这就是"可逆效应（Revertible Effects）"的全部要求。

为什么要"写在一起"？这是**局部性（Locality）**原则：拆装逻辑放在同一处，开发者就不会忘记——忘了写清理逻辑是泄漏的头号原因。VSCode 的 `deactivate` 钩子之所以没用，恰恰因为它违反了局部性：创建效应的代码在 `activate` 里，销毁效应的代码在遥远的另一个函数里，两者之间隔着几千行，漏写一个就是泄漏。

### 解法 2：自动记账——ctx.effect

"每次自己返回撤销按钮"听起来简单，但要求每个开发者都自觉遵守，等于没有约束。Cordis 的核心设计是：**把记账变成框架的职责**。

所有会改变环境的操作，都必须经过一个唯一的入口——`ctx.effect`：

```ts
// Cordis 真实实现（fiber.ts，节选）：
effect(execute: () => Effect, label = 'anonymous') {
  this.assertActive()

  const disposables: Disposable[] = []
  const dispose = () => {
    let task!: void | Promise<void>
    // ★ 核心：逆序执行所有撤销动作——后注册的先撤销
    for (const dispose of disposables.splice(0).reverse()) {
      if (task) {
        task = task.then(dispose)      // 异步撤销按序串成链
      } else {
        const result = dispose()
        if (isObject(result) && 'then' in result) {
          task = result as any
        }
      }
    }
    return task
  }
  // ...执行 effect，把产生的每个"撤销按钮"收集进 disposables
  // ...返回包装后的 dispose 函数
}
```

两件事发生了：

1. **收集**：`execute()` 执行你的副作用代码，它返回的每一个"撤销按钮"（dispose 函数）都被收进 `disposables` 列表——这就是**记账**。
2. **逆序执行**：`dispose()` 撤销时，对列表 **`.reverse()`** 后依次执行——**后注册的先撤销**。

为什么必须逆序？想想叠盘子：先装插件 A（打开文件），再装插件 B（往文件里写了配置）。撤销时必须先撤 B 的写入、再关 A 的文件——顺序反了，B 会往已关闭的文件里写东西。这就是后进先出（LIFO）。这行 `.reverse()` 就是整个可逆性理论在工程上的落点。

而且，`ctx.effect` 接受的不只是普通函数——它支持**生成器**：

```ts
// 效应迭代器：一次 effect 里做多步，每步 yield 一个撤销按钮
ctx.effect(function* () {
  const file = yield openFile('log.txt')      // 第一步：开文件
  yield startTimer(5000, tick)                // 第二步：开定时器
  // 撤销时自动按逆序：先停定时器，再关文件
})
```

这让你可以在一个效应里编排多步有依赖的操作，而框架保证撤销顺序永远正确。

### 解法 3：像插线板一样组织——上下文与派生

现在每个效应都可逆了，但还有一个问题：**效应属于谁？**

一个大型系统里，插件 A 和插件 B 都调用了 `ctx.effect`。卸载 A 时，怎么知道哪些"撤销按钮"是 A 的、哪些是 B 的？

Cordis 的答案是**上下文树（Context Tree）**——这是整个设计里最优雅的部分：

```
        根上下文（root）
           │
      ┌────┴────┐
   插件A上下文  插件B上下文     ← 每个插件拿到一个"派生的"子上下文
      │
   ┌──┴──┐
 A的子插件们                 ← 子插件再派生，形成树
```

实现上，派生用的是 JavaScript 的原型链——`context.ts` 真实代码：

```ts
extend(meta = {}): this {
  const self = Object.create(getTraceable(this, this))   // 原型链继承父上下文
  for (const prop of Reflect.ownKeys(meta)) {
    Object.defineProperty(self, prop, ...)               // 覆盖自己的字段
  }
  return self
}
```

**插线板比喻**（来自 Cordis 作者的原文）：上下文是插座，插件是插头。墙上的插座是根上下文；插线板是插在插座上的"插座"——它自己用电，又提供新的插孔（派生上下文）；插线板上还能再插插线板。**拔掉一个插线板，插在它上面的所有东西跟着断电**——卸载父插件，级联卸载所有子插件。

这就是"高阶资源"的直观含义：一个给别的插件提供 API 的插件，占用的资源是"能占用资源的资源"，所以上下文类型必须是递归的。数学上写作 $\mathcal{C}_{n+1} = \mathcal{C}_n \times (\mathcal{C}_n \to \mathcal{C}_n)$——工程上就是这 5 行原型链代码。

### 解法 4：把依赖变成声明——服务（Service）

时间维度解决了，轮到空间维度（依赖管理）。

Cordis 的规则：**插件不直接 import 依赖，而是声明"我需要什么"，框架保证"你需要的东西就绪前你不会启动"**。

```ts
// 一个需要数据库的插件：
const myPlugin = Object.assign(
  (ctx: Context) => {
    // 在这里可以放心使用 ctx.database —— 它一定已经就绪
    ctx.database.query(...)
  },
  { inject: ['database'] }   // ← 声明：我需要 database 服务
)

// 提供方：
class Database extends Service {
  constructor(ctx: Context) { super(ctx, 'database') }
}

await root.plugin(Database)     // 先提供
await root.plugin(myPlugin)     // 后消费——但顺序其实无所谓
```

`inject: ['database']` 是声明式的：myPlugin **声明**了依赖，加载时框架会检查 database 是否已提供——没提供就**等着**，提供了才激活。这就是第 3.2 节的理论：依赖满足性（Satisfaction）是一个可判定的谓词。

**依赖方、提供方彻底解耦**：提供方换实现、甚至运行时被替换，依赖方都会自动感知并重新激活。这正是 Koishi 生态 4000 个插件能协作的原因——插件作者之间不需要任何沟通，只需要对"database 这个名字"达成共识。

### 解法 5：卸载的安全顺序——守卫（Guard）

最后一个也是最微妙的问题：**卸载一个还在被依赖的服务，怎么办？**

场景：B 插件正在用 A 提供的数据库连接池。你卸载 A：

- 如果 A 直接关掉连接池 → B 正在进行的查询全挂
- 如果 A 什么都不做 → 泄漏

正确答案是：**A 必须等 B 先优雅退出，才能关闭连接池**。而且 B 退出时（运行自己的清理代码）可能还需要访问 A——所以 A 的绑定在 B 退出**期间**必须保持可用。

这是全论文最精妙的一个实现，真实代码只有几行（`reflect.ts` 的 `provide` 方法）：

```ts
provide(name: string, value?: any) {
  return this.ctx.fiber.effect(() => {
    // 提供：把值放进服务表
    this.store[key] = impl
    if (ACTIVE) this.notify([name])        // 通知依赖者们："我上线了"

    return async () => {                   // ← 撤销按钮（卸载时执行）
      delete this.store[key]               // ① 先摘牌："我不再提供这个服务了"
      const fibers = this.notify([name])   // ② 依赖者们感知到变化，开始自己的退出流程
      await Promise.allSettled(            // ③ 守卫：等所有依赖者退出完毕
        fibers.map(fiber => fiber.await())
      )
      delete this.ctx.fiber.store![name]   // ④ 全部退出后，才清理自己的表
    }
  })
}
```

这个四步顺序是精心设计的：

1. **先摘牌再等待**——依赖者立刻感知"服务没了"，触发自己的卸载；但此时值还在表里，**依赖者退出途中仍能访问它**（连接池还在，B 可以把连接还回去）
2. **等待全部落定**——`fiber.await()` 等的是每个依赖者的**惯性状态机**跑完（见下节），一个都不能漏
3. **最后才清理**——保证没有依赖者会访问一个已经清空的表

这就是论文定理 63 的工程实现：**提供者的撤回排在它所引发的全部停用之后**。死锁怎么办？不会——因为"摘牌"使依赖者算不出满足的目标，它们必然退出；等待者只等"已经不可满足"的纤维，依赖图按需遍历而非预先分析，环不会无限等待（无环性是声明层面可检查的）。

### 解法 6：热替换的惯性状态机

有了可逆效应和守卫，最后一块拼图是：**迁移过程本身**（加载/卸载）可能耗时（异步 I/O、网络请求），期间依赖关系又变了怎么办？

Cordis 的答案是每个插件实例（称为**纤维 Fiber**）都跑一个六态状态机：

```
            ┌──────────────┐
   加载指令 │              │ 依赖就绪
  ─────────►│   PENDING    ├──────────► LOADING ──┬── 目标没变 ──► ACTIVE
            │ (等待依赖)    │       执行插件代码     │
            └──────────────┘                      └── 目标变了 ──► UNLOADING
                                                                    │
      UNLOADING ──┬── 依赖仍不满足 ──► PENDING（或 DISPOSED）       │
                  │                                                    │
                  └── 依赖又满足了 ──► LOADING（链回加载！）◄──────────┘
```

核心代码（`fiber.ts`）：

```ts
export const enum FiberState {
  PENDING,    // 等待依赖满足
  LOADING,    // 正在加载（执行插件代码）
  ACTIVE,     // 运行中
  FAILED,     // 加载出错（记录错误，不再重试）
  DISPOSED,   // 已被父级卸载
  UNLOADING,  // 正在卸载（执行撤销链）
}

private _setEpoch(epoch: string) {
  const oldEpoch = this._runner.epoch
  if (epoch === oldEpoch) return
  this._runner.epoch = epoch
  if (this.inertia) return        // ★ 惯性：一次迁移未完成，不响应新变化
  this._updateState(() => {
    if (epoch !== INACTIVE && oldEpoch === INACTIVE) {
      this.inertia = this._reload()     // 启动加载
    } else {
      this.inertia = this._unload()     // 启动卸载
    }
  })
}
```

两条关键规则：

1. **惯性（Inertia）**：`if (this.inertia) return`——迁移一旦启动就**跑到底**，中途依赖关系再变化也不打断（异步操作无法安全中断，强行打断会导致半加载状态）。新变化先记下，等当前迁移完成后再响应。
2. **链式衔接**：加载完成时检查目标——没变就进入 ACTIVE，变了就**直接链入卸载**；卸载完成时同样检查——依赖又满足了就**直接链入加载**。这个互递归保证了系统永远不会卡在中间态。

一个真实场景：你在开发中修改了插件的配置文件。框架检测到变化 → 旧纤维进入 UNLOADING（撤销旧版一切）→ 链入 LOADING（加载新版）→ 新的 ACTIVE。**全程进程不重启，其他插件的状态原封不动**——这就是热更新（HMR）的底层机制。

## 第三部分：整体设计——三个组件拼成一张图

把上面的解法拼起来，Cordis 的完整架构是这样的：

```
┌──────────────────────────────────────────────────────┐
│                    应用层（你的代码）                    │
│    插件A    插件B    插件C    （每个都是可拆卸的组件）    │
└──────────────────────┬───────────────────────────────┘
                       │ 每个插件拿到派生的子上下文
┌──────────────────────▼───────────────────────────────┐
│              Context（上下文 = 插线板）                  │
│  · ctx.effect()   ← 所有副作用唯一入口，自动记账          │
│  · ctx.provide()  ← 提供服务（带守卫式撤销）             │
│  · ctx.plugin()   ← 挂载子插件（子生命周期=父的效应）      │
│  · ctx[key]       ← Proxy 属性访问（声明了才能读）        │
└──────────┬────────────────────────┬──────────────────┘
           │                        │
┌──────────▼──────────┐   ┌─────────▼──────────────────┐
│  Registry（注册表）   │   │  Reflect（反射 + 通知）      │
│  · 插件→运行时映射    │   │  · 服务表（store）           │
│  · 纤维计数/分配 uid  │   │  · 依赖变更 → notify →      │
└─────────────────────┘   │    所有相关纤维重评估目标     │
                          └────────────────────────────┘
┌──────────────────────────────────────────────────────┐
│              Fiber（纤维 = 插件实例的生命周期）           │
│  PENDING → LOADING → ACTIVE → UNLOADING → ...         │
│  · disposables：撤销链（LIFO）                          │
│  · inertia：迁移句柄（惯性保证）                         │
│  · epoch：目标视图摘要（依赖解析的指纹）                   │
└──────────────────────────────────────────────────────┘
```

**数据流**：一切变更（提供/撤销/加载/卸载）都归结为"某个服务的提供状态变化"→ `notify` 广播给所有声明了该依赖的纤维 → 每个纤维重算自己的**目标视图**（epoch，由提供者 uid 拼接的字符串）→ 视图变了就驱动状态机迁移 → 迁移执行/撤销效应链 → 完成后再检查（链式衔接）。

**为什么这个设计是自洽的**——三句话：

1. **时间维度**：每个效应带逆 + LIFO 撤销链 → 卸载即精确还原（定理 7、16）
2. **空间维度**：声明式依赖 + 守卫式撤回 → 激活/停用自动排序（定理 63、64）
3. **组合维度**：惯性状态机 + 链式衔接 → 任何装卸序列收敛到同一静止状态，路径无关（定理 73 汇合性）

对应到论文的语言：前两条是"局部保证"，第三条是"全局保证"。2026 年的 88 页论文做的，就是把这三句话**形式化为可证明的定理**——包括无死锁（Progress）、收敛唯一（Confluence）这样听起来像操作系统教材的命题，在插件系统上第一次被完整证明。

## 第四部分：引申——这套东西为什么重要

### 引申 1：数学不是装饰品

你可能注意到前面出现了幺半群、群、同态这些词。它们不是学术炫技，每个都对应一个真实的工程 bug：

| 数学概念 | 工程含义 | 没有它会怎样 |
|---------|---------|-------------|
| 幺半群（封闭性+结合律） | 插件组合无歧义 | 两个插件互调顺序行为不同，系统不可预测 |
| 群（每步有逆） | 每个操作可撤销 | 忘了写清理 → 静默泄漏（VSCode 87% 的现状） |
| 同态（effect(f∘g) = effect f ∘ effect g） | 分开记账=合并记账 | 复合插件的撤销链错误 → 热更新后状态错乱 |
| LIFO 顺序 | 后装先拆 | 撤销顺序错 → 访问已关闭的资源 |
| 汇合性（路径无关） | 最终状态只取决于最终配置 | 生产 bug 无法复现 |

### 引申 2：边界哲学——什么能撤销，什么不能

Cordis 的诚实体现在它划了一条**系统边界**：

- **边界内**（获取阶段）：打开文件、建立连接、注册监听——这些**可以**被撤销，效应系统完整追踪
- **边界外**（发射阶段）：发出的网络请求、写入外部系统的数据——这些**无法**撤销。你没法"撤回"一封已经发出去的 HTTP 请求

对于边界外，只有两个办法：**扣留**（等状态确定再发——像事务提交）或**补偿**（发错了发一封更正——像退款）。论文把这个二分讲得非常清楚，这是做任何"可恢复系统"都绕不开的设计判断。

### 引申 3：与其他方案的对比光谱

| 方案 | 做到的可逆性 | 代价 |
|------|------------|------|
| React useEffect | 效应配 cleanup | 不可组合（不能嵌套/异步），复合撤销无从推导 |
| OSGi / iPOJO | 服务出现消失自动激活停用 | 清理回调手写+同步，资源安全靠纪律 |
| Erlang/OTP | 热代码升级+监督重启 | 进程粒度粗，重启丢状态 |
| 软件事务内存（STM） | 自动回滚 | 只限内存操作，作用域固定 |
| **Cordis** | 任意效应可逆 + 组合保持 + 依赖响应式 | 所有变更必须经过 ctx（纪律性约束） |

Cordis 的独特点：**它是唯一把"效应配对逆 + 组合性保持 + 响应式依赖"三件套同时做到并形式化证明的系统**。

### 引申 4：为什么 DeepSeek 选了它——自进化智能体的前景

回到最开头的场景。聊天机器人要热插拔插件已经够难了；DeepSeek 面对的问题更难一个量级：

> 未来的 agent harness 里，**AI 自己**生成新工具、替换旧策略——以秒为频率、几乎无人工监督。

- 每次自我修改都重启 → 会话状态全丢、任务反复中断
- 一次有 bug 的自我修改把恢复系统搞挂 → 死循环
- 依赖拓扑高频变化 → 手写协调不可能

Cordis 的三个性质恰好是解药：可逆（改坏了自动回滚到改动前）、响应式（依赖变化自动重排激活顺序）、汇合（无论怎么折腾最终状态只取决于最终配置）。这就是为什么 dsh 的 54 个包——agent loop、工具注册表、模型适配器——**全部**是可热插拔的 Cordis 插件：任何一部分都能在会话进行中被替换而不丢上下文。

论文在结论里点明了这条路线：**自进化智能体脚手架是这套理论的下一个验证战场**。你今天看到的 dsh，是这个愿景的第一版。

### 引申 5：留给语言的作业

Cordis 的局限也很诚实：它**不能**保证资源安全——插件里写一个全局变量、调一个没封装的底层 API，就绕过了整个体系。作者的畅想是：未来的编程语言可以——

- 把全局变量和未封装 API 标记为 `unsafe`（Rust 式），编译器证明"不含 unsafe 的代码资源安全"
- 用代数效应（Algebraic Effects）语法让编译器为效应迭代生成状态机，替代运行时闭包
- 把依赖声明放进类型系统（Haskell typeclass / Rust trait 已能做到一半）

Cordis 的路线是**渐进式**的：不要求换语言，用主流 OOP 语言就能落地，代价是"所有变更必须经过 ctx"这个纪律。这是它能被 Koishi（4000 插件）和 DeepSeek（54 包）迅速采用的根本原因。

---

## 结语：一句话记住这套系统

> **可逆插件系统 = 每个副作用配一个撤销按钮 + 框架自动记账逆序撤销 + 依赖声明驱动自动排序 + 惯性状态机保证迁移完整。**

工程上它只是 2000 行 TypeScript；理念上它把"软件如何安全地改变自己"这个问题从"重启大法"推进到了"精确到单个插件的热插拔"。当软件开始自己修改自己（AI agent 时代），这套东西就从"锦上添花的框架特性"变成了"基础设施级的要求"。
